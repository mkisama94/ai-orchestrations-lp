## 5. コンテンツ実装要件

### 5.1 ヒーロー・ナビ・CTA

- H1は構成案のメインコピーを1つだけ使用。プロジェクト正式名称はその上の補助見出しにする。
- 主CTAは `#contact`。補助CTAは `#power-candidates`。ヘッダーの当該ページ用相談ボタンも同一ページ内へ。
- 公表値は「4変電所」「公表供給可能量50〜300MW」。50MWのIT負荷、確保済み容量、予約枠に読み替えない。
- メインコピー、主ボタン、最小限の数値・条件をスマートフォンで読みやすい順に表示。動画・自動スライドを初版の必須要素にしない。
- モバイル固定CTAはフォーム付近で隠すか通常配置へ切り替え、入力欄・送信ボタン・同意欄を覆わない。本文末尾に必要な余白を確保する。

### 5.2 電力カード・地図

- 4変電所の名称・供給可能量・工期・出典を根拠資料どおりに掲載。個別出典リンクを各カードに付ける。
- 「約2年半」の近くに契約締結から連系までという起点を表示。適用条件をツールチップだけに隠さない。
- 公表情報と案件確認状況を視覚的に区別する。未確認は「確認対象」とし、0・空欄・確保済みに置換しない。
- 4カードの後に送電線7件を加えた全11設備の一覧を置く。設備種別を明示し、容量を合計しない。
- 初版地図はエリア概略に限定。設備の正確な座標を取得していない状態で推測ピンを置かない。敷地・供給圏・回線ルートを表す形状を創作しない。
- 具体的候補地を追加する際は「案件ID／所在地の公開範囲／面積／権利・造成／受電検討／通信検討／災害調査／情報基準日」を1組で管理する。現在の電力カードをそのまま土地物件カードと扱わない。

### 5.3 地震比較表と指標説明

- 正本は `data/seismic-comparison.json`。22地点すべてを掲載し、町名・丁目、メッシュ、出典を追えるようにする。
- 表題は「全国のDC立地・開発地域等の代表地点比較」。全地点が分譲中・50MW建設可能な用地であるとは書かない。
- 初期表示は3列：地点、2024年基準の30年間・震度6弱以上、同・6強以上。全22行を表示。詳細切替で周辺幅・PGV・増幅率を追加。
- JavaScriptが動かない場合にも、全数値と注記を読める静的表を残す。詳細切替は見た目の補助とする。
- 確率は小数1桁、PGVは小数1桁、地盤増幅率は小数2桁。計算・並べ替えには丸める前の値を使用。
- 周辺幅は代表点から東西・南北約500m間隔の9点。堺8点・福岡6点の有効値を明記し、欠測を0にしない。
- 地盤増幅率はすでに地表PGVと確率に反映されている。再乗算しない。確率からPMLや停止率を計算する機能は作らない。
- グラフを追加する場合は全地点・共通軸・ゼロ起点とし、棒の長さでDCの安全性を格付けしない。初版では表を優先する。
- 常時見える注記に「2024年基準」「町名代表点」「PML・停止確率ではない」「2025年の海域活断層評価等の再反映ではない」を含める。長いモデル説明は開閉欄でよい。
- 受電候補の地図と地震比較の地点を自動でひも付けない。例：「新能登300MW＋輪島1.4%」を一つの敷地の評価として並べない。
- 表の下に6項目の意味、投資家・需要家それぞれの確認事項を掲載する。PMLの欄を追加する場合は「未評価」とし、仮の数値を入れない。

### 5.4 補助制度・分散案・プロジェクトの状況

- 補助率には対象地域、新設か増設か、基礎要件と上限を対応させる。詳細は根拠資料から使用する。
- 分散案をヒーローに戻さない。受電区分の境界は「2,000kW未満」。IT設備だけで1,990kWなら高圧でよい、という例は使わない。
- 一棟・単一敷地・県内複数拠点を区別する。各案の容量合計を同じ学習性能と表現しない。
- 進捗の初期公開文言は「50MW級を軸に、立地・事業条件を検討中」。用地・電力確保を示す書面を確認した場合だけ、該当する範囲・基準日を添えて更新する。
- 「県公認」「電力会社と共同」「大手需要家確定」「PML10%未満」「即納」「最安」等は、今回の資料では裏付けられていないため原稿に含めない。
- 未確認事項の内部メモは制作管理表に置き、公開本文へ「公開前に要確認」といった作業指示を残さない。

## 6. 問い合わせフォームと送信完了

### 6.1 初版で動く構成

既存フォームは `https://tally.so/embed/obPAq1`、代替リンクは `https://tally.so/r/obPAq1`。Tallyの編集権限・現在の項目設定は本調査では確認していない。

LP本体の刷新は既存フォームを利用して進められる。フォームの上に「データセンター立地／投資・事業参画／用地・協業」の相談種別と、任意で伝えてほしい容量・時期の案内を置く。既存フォームの相談欄に記入できることを制作時に実画面で確かめる。

自動入力を実装する場合は、Tallyに存在する実際の項目・hidden field名を確認する。未設定のURLパラメータや架空の項目IDを付けて、案件識別・入力内容が保存されると見なさない。既存フォームで必要事項を受け取れない場合は、受付担当が管理する専用フォームを設定してから差し替える。

### 6.2 専用フォームにする場合の項目案

| 項目 | 必須 | 入力内容 |
|---|---|---|
| 会社・組織名 | 任意 | 個人の用地所有者も相談できる |
| 氏名 | 必須 | 自由入力 |
| メールアドレス | 必須 | 返信先 |
| 相談種別 | 必須 | DC建設・運営／計算資源の利用／投資・事業参画／用地・協業／その他 |
| 相談内容 | 必須 | 要件が未定でも記入できる短文欄 |
| 希望容量・用途・時期 | 任意・開閉欄 | 容量は数値＋単位＋「受電容量／IT負荷／未定」を組にする |
| 個人情報の取扱いへの同意 | 必須 | 実際のプライバシーポリシーへリンク |

電話番号、詳細予算、機密図面、確定した設備仕様は必須にしない。添付資料は初版で求めず、必要なら初回相談後に共有方法を案内する。受付担当・通知先・返信手順は事業責任者が設定する。未確認の「24時間以内に回答」「無料診断」は載せない。

### 6.3 送信処理の修正要件

1. 現在の `new URL('thanks.html', window.location.href)` を、同一オリジンの `/thanks.html` を指す処理へ変更する。実装時の例は `new URL('/thanks.html', window.location.origin)`。
2. 既存の `event.origin === 'https://tally.so'`、送信元ウィンドウ、イベント名、正しいフォームIDの照合を保持する。別フォームを採用した場合は、実IDを設定と処理の両方に反映する。
3. 完了イベント以外では完了ページへ遷移しない。iframeの読み込み・送信ボタンのクリック・一般のpostMessageを送信成功として扱わない。
4. 送信後の遷移・計測の責任は1つの処理にまとめる。二重登録・二重計測を防ぐ。
5. フォームが読み込めない場合も、別タブで開くリンクと相談窓口の説明を表示する。画面を「読み込み中」のまま放置しない。
6. 別タブ版の送信後動作もTally設定を確認し、受付完了が分かる画面とサイトへ戻るリンクを用意する。サイト側のiframe用イベントは別タブ版には届かない前提で扱う。
7. 読み込み失敗・入力エラーでは内容と次の行動を示す。Tally側で管理するエラーは実画面の挙動を確認し、LPに見せかけの成功表示を追加しない。

## 7. 表示・アクセシビリティ

- レイアウト確認幅は320、375、768、1440px。本文全体の横スクロールを起こさない。横に長い詳細表は表の枠内だけでスクロール可能にする。
- 表にはcaption、行・列見出し、単位、出典を付ける。詳細列の切替ボタンはキーボード操作と状態通知に対応する。
- モバイルの候補カードは1列。本文16px程度を基準とし、成立条件・出典を読めない極小文字にしない。リンクやCTAは十分なタップ領域を持つ。
- 見出し順、フォーカス表示、色のコントラストを確認。色だけで「能登」「比較地域」「確認状況」を伝えない。
- 固定ヘッダーの高さに合わせて `scroll-margin-top` を指定し、旧アンカー・新アンカーとも見出しが隠れないようにする。
- 装飾画像には空の代替テキスト、説明図には同等の本文説明を用意。数値・注意条件を画像だけに閉じ込めない。
- 動きを減らす設定に対応し、不要な常時アニメーションは使わない。
- 画像の幅・高さを指定し、フォーム領域の高さを確保して表示の飛びを抑える。初版の独自画像は合計1MB程度を制作目安とする。
- Tallyと既存計測以外の外部スクリプトを安易に増やさない。Lighthouse等で主な遅延要因を確認し、実測のない速度保証を報告しない。

| イベント | 発火条件 | 個人情報を含まない属性例 |

| 電力 | 4変電所・全11設備の数値が一次資料と一致。容量合算なし。工期の起点・約100mの条件が読める |
| MWの意味 | IT負荷と受電容量が区別され、2,000kW未満の境界が正しい |
| 地震 | 22地点・全指標・個別リンクがJSONと一致。2024基準と調査日を別に表示。PML・安全順位への読み替えなし |
| 欠測 | 周辺194有効点、堺8点・福岡6点。欠測を0として計算していない |
| 資料 | CSVの文字化け・列・単位・モデル条件・出典を確認。ページと配布物で値が一致 |
| 遷移 | 主CTA、全内部リンク、旧アンカー、出典、資料リンク、プライバシーが有効 |
| フォーム | 実際の項目・必須エラー・読み込み失敗・別タブ経路が確認されている |
| 送信完了 | 許可されたテスト送信で受信を確認し、正しい完了ページへ到達。無関係なメッセージでは遷移しない |
| 表示 | 4画面幅で重なり・見切れ・本文横スクロールなし。固定CTAが入力を妨げない |
| 操作 | キーボードでナビ・FAQ・表切替・フォームへ到達。JS無効でも主要内容を読める |
| 共通回帰 | トップ、他プロジェクト、共通フォーム、ナビ、完了ページに意図しない変化がない |
| SEO・計測 | canonical・OG・構造化データが内容に対応。イベントの二重発火・個人情報送信なし |
| 公開確認 | 公開版のURL・主要ファイル・完了先・配布物を再確認し、ローカルと本番を区別して報告 |

低影響の文言変更に細かい単体テストを大量追加する必要はない。数値照合、URL解決、送信イベントの検証、実際の操作経路を重点的に確認する。問い合わせの本番テストは、受付担当と合意したテスト内容・環境で行い、実在顧客を装わない。
